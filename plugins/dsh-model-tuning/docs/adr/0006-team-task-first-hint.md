# 团队任务先行提示：只做可选的一段提示词，不碰上游工具

观察到的事实：上游 `TEAM_POLICY`（`dsh-tool-agent-team/src/index.ts:27-33`）只讲「list → get → claim → 干活 → complete」这套**消费**流程，从未要求 Lead「派活前先建任务」。于是 Lead 可以直接 `subagent` 派活，子智能体去 `team_task_list` 拿到空数组——那一次工具调用白烧，还可能据此推断出"没有工作"。

这不是 bug：任务板按根会话隔离、空板如实返回 `[]`、UI 渲染成「暂无结果」都正确。**它是流程缺口**，而本插件「新会话默认开团队」会把它放大到每个会话。

可选干预点只有三处：上游工具/提示词（要改 asar 或等上游）、插件自己加一段 systemPrompt、或者什么也不做只写文档。

## Considered Options

- **改上游 `TEAM_POLICY`**：最对症，但要在打包产物里改字符串，比 xhigh 的三处小改脆弱得多，且上游随时会重写。
- **发一个 skill**：零前缀成本，但子智能体不主动加载就仍然会盲查——治不到实际症状。
- **只写插件页文案**：等于没修。
- **插件加一段可选 systemPrompt（采纳）**：命中「派活前先建任务 / 空板就报告」这一句话，默认关，可单独关。

## Consequences

- 默认关：装插件、开团队默认都不会改变提示词。用户显式打开后，**只对团队模式已开启的会话**注入，其他会话拿到空字符串（不占位）。
- 它**改变提示词前缀**。走指纹敏感中转站的部署需要自行评估（本工作区的 `dsh-clean-route` 就是为此存在），所以开关说明里写明这一点，并且它与「团队默认」是两个独立开关，不联动。
- 正文紧邻上游英文 `TEAM_POLICY`，因此也用英文，避免模型把中英两段当成两套规则。
- 装配时读状态、每次装配重建文本，所以开关即时生效，不需要重载插件。
- 本条不改变「不是 bug」的判断：上游若日后在 `TEAM_POLICY` 里补上同样的约束，本开关可以直接删掉。
