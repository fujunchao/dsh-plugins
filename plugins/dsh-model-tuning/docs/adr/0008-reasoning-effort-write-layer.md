# 档位写到哪一层，取决于该路由在配置里有没有显式 models

`llm-pi-ai` 的两条路语义相反，而 `models` 与 `modelOverrides` 在同一 profile 里**互斥**（同时出现会被显式报错）：

- `models` 非空 = 这张表就是该路由的全部模型（"整段替换目录"）。
- `models` 缺省或空数组 = 服务完整已安装目录。
- `modelOverrides.<id>` = 只覆盖列出的字段，其余仍取目录；且 id 必须存在于目录里。

原实现（`lib/tune.js` 的 `buildModelOps`）对所有路由都整段替换 `models`。对"用户已经手写了 models"的路由（本机的 `deepseek`、`google` 都是这种）这是对的；对真正走继承目录的路由，则会把整张目录物化进 `cordis.patch.yml`——pi-ai 以后新增的模型会被这份旧快照永久盖住，且很难归因。

## Decision

按**实际配置层**判断，而不是按 `declared`：

1. 该路由在配置层（`base`/`user` 合并）里有显式 `models` 数组 → 在它上面整段替换（现状行为不变）。
2. 没有显式 `models`、模型是从已安装目录继承来的 → 写 `modelOverrides.<id>`。
3. 两条路都不写空值：`off` 档允许 `null`（表示"支持但不发参数"），其余档必须是非空字符串，且至少要有一个非 `off` 档，否则 `llm-pi-ai` 拒写。

## Consequences

- `declared` 与"是否物化目录"无关：手写路由必然有显式 `models`，而目录路由也可能有（本机 `google` 就是）。判断必须看配置层，不看适配器算出来的标志。
- 目录路由的模型列表里出现"只在目录里存在"的模型时，界面要标明它是继承来的，用户才不会以为"删掉它"能把它从目录里去掉。
- 这条规则也决定了"新建供应商"只能走 `models`（新供应商没有任何目录继承）。
