# 供应商区块接管就地编辑；默认档位分两层，模型档存在插件状态里

2026-11-19 定契（Q1–Q18 逐条确认）。起因是两条用户反馈：供应商区块的模型行只有「删除」没有「编辑」；「添加模型」表单里没有"这个模型默认用哪一档"。

三件事让这个决定不是简单的"加个按钮"：

- **契约欠债**：`plan.md` 的 v2 增补本写着「展开看模型行（可加/删/改档位）」，实现只有加和删。
- **上游没有模型级默认档位这个槽位**：模型只有 `id/name/contextWindow/maxTokens/input/reasoningEfforts/compat` 七个字段；`reasoningEfforts` 是"支持哪些档 + 各档 wire 写法"，不是默认值。能表达"默认档"的只有 **provider 级 `reasoning`**（整条供应商一个值，语义是"调用方省略档位时兜底"，并被报成模型的 `defaultEffort`，composer 换模型时会先把它写进选择）。
- **`models` 是数组，`id` 只是元素字段**，所以原生页本来就能就地改 id；真正的字典键只有 `providers` 的 route id 和 `modelOverrides` 的 id。这条推翻了"改 id 只能删旧建新"的原有判断。

## Decision

1. **编辑 = 字段写入，落在「供应商」区块，行内展开、按行保存。** 一个字段只有一个家：
   - 模型行可改：显示名、上下文窗口、最大输出、输入模态、思考等级声明、模型默认档位与锁定、模型 id。
   - 供应商头可改：显示名、baseURL、协议 `api`、密钥内容。
   - 只读：route id、`apiKeyEnv` 引用名（凭据引用名沿用 `<ROUTE>_API_KEY` 派生规则，原生也不许改）。
   - `compat`、提供商级 `defaultContextWindow`/`defaultMaxTokens`/`defaultInput`、`thinkingBudgets`、供应商默认档位仍只归「模型高级字段」区块。

2. **模型 id 可以改**，但必须一次原子写完成，且只迁移插件能负责的引用：显式 `models` 路由改数组元素；目录路由的 `modelOverrides` 改键（unset 旧 + set 新，同一批 ops）；插件状态里指向旧 id 的「插件默认」同批改写。**会话日志里的历史选择不迁移**——原生页改 id 后同样如此。

3. **默认档位分两层**：
   - **供应商默认档位**写 `provider.reasoning`：上游原生，请求兜底与 composer 预填都认，原生页也看得到；
   - **模型默认档位**写插件状态文件（`~/.dsh/model-tuning.json`）：仅在插件启用时生效；
   - 模型留空 = 继承供应商默认档位；模型默认档位必须落在该模型的思考等级声明集合里（声明改小后要联动校验）。

4. **锁定优先于保持**：每个模型一个锁定标记，显式设置模型默认档位时默认打开。锁定模型被选中时套用其默认档位；未锁定的模型仍走「档位跨模型保持」。

5. **判据与目标值分离**：判据沿用 ADR 0005 的等式（事件里的档位为空、或恰好等于目标模型的自动档 ⇒ 视为自动），锁定只改变"要写成什么"。两条规则合成**一个决策函数、一个 `session/event` 监听器、一个去重集合、一次追加**——两个监听器会各自 append 同一次 selection，现有去重（闭包内的 `corrected`、键不含目标档位）挡不住。

6. **撤销合并成一颗「撤销上一次写入」**：编辑也落快照，撤销后提示动作与对象（如"已撤销：编辑 GLM-5.3 的档位"）。因为恢复是**整条 provider 覆盖**，撤销前必须复核该 provider 当前值是否仍等于上次写入后的值，不等就要求二次确认。

7. **已存在的供应商也要有「检测连通」**（ADR 0007 要求的显式校验此前只活在新建表单里），而且它必须探**表单里的新值**、不是已保存的旧值：`/discover` 的 `{route}` 形式接受 `baseURL` / `api` 覆盖（密钥仍按该 route 的 `apiKeyEnv` 从凭据服务取，只在宿主侧使用）。改 baseURL 或协议后，保存前要求先检测；但"探测不出模型"的端点不该把用户锁死，所以门禁做成**软门禁**：没检测成功就保存要二次确认。保存时宿主会复验该供应商是否仍可用（协议与现有 models 不兼容会被拒），拒绝就保持原值、不半途改。

## Considered Options

- **只用 `provider.reasoning` 做默认档位**：零新机制，但整条供应商只能有一个值，而诉求正是"Flash 低、5.3 高"。
- **给模型造一个上游没有的默认档字段**：schema 会拒写，等于发明私有配置方言。
- **请求级改档**（`prepareCall` / `llm/stream`）：请求最可靠，但会话里显示 max、实际发 high，排查时无从下手。
- **接管 composer 的模型槽**：宿主只提供只读标签（`conversation.input.model.*`），做不到。
- **模型 id 只读、要改就删了重建**：对一个只有 1 个模型的供应商，删最后一个模型等于删整条供应商连同派生凭据。
- **自定义 `apiKeyEnv` 引用名**：原生都没有这个能力，会引出第二套凭据引用规则。
- **两个撤销按钮 / 编辑用弹窗 / 默认档位必填 / 冲突时字段级自动合并**：都会把"我刚才那步是什么"和"谁改的"变成用户要自己推理的问题。

## Consequences

- 插件页开始与原生 Models 页**覆盖同一批字段**：两边同写 `llm-pi-ai`、按 revision 报冲突。`plan.md` 里"不编辑 `contextWindow`/`maxTokens`/`input`"一条被本条取代；`retryPolicy`/`timeoutMs`/`headers` 仍不碰。
- 停用插件后，模型默认档位与锁定失效，只剩 `provider.reasoning`——这是"插件策略 vs 供应商能力"分层的结果，不是缺陷。
- 换模型时接口会**闪一下**（先显示原生注入的自动档，微任务里改成锁定档）。已接受，换来的是会话记录里就是真实档位。
- 撤销是整条覆盖，没有第 6 条那层复核就会连带抹掉原生页的改动。
- ADR 0005 写的"补正后仍等于默认档则记 warn 并放弃"**从未实现**；本次以实测行为为准（判定不成立即静默返回，只有 `select()` 抛错才 warn）。
- 状态文件是字段白名单（`version` 恒为 1），新增 `modelEfforts` 一类字段必须同时改 `emptyState()` 与 `normalizeState()`，漏一处会被静默丢弃。
